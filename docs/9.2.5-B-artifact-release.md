## 3. Builds e testes Maven/Docker

`build-app` confere origin exata, HEAD completo e árvore limpa; gera `git archive`
do SHA, registra checksum e extrai em diretório novo. Não copia target, .env
ignorado ou arquivos não rastreados. Rejeita symlinks/traversal do snapshot.
O build usa `mvn -o -B -ntp clean verify` com settings globais/de usuário vazios,
Java21 e ambiente reduzido. AWS environment/OIDC não são herdados; configurações
AWS vazias e metadata desativado isolam também o SDK dos arquivos de credenciais
do usuário. DOCKER_CONFIG vazio já é definido antes dos testes Maven. Não aceita
relatórios de um target anterior.
Saídas brutas de Maven não são impressas ou incluídas no manifesto.

A aprovação exige relatórios Surefire/Failsafe, testes executados, zero erros/
falhas/skips e JaCoCo **LINE >=80%** por aplicação. Auth possui um IT condicionado
a `-Dauth.internal.image`: o skip desse teste específico só é tolerado durante
a preparação da imagem. Depois do build, o executor roda `verify` com a imagem
efetivamente construída e exige relatório sem skips; até lá não aprova artefatos.
Não permite usuário substituir teste/cobertura por booleanos.

Os quatro Dockerfiles são multistage Java21, compilam fontes próprias e copiam
JAR do estágio build, com usuário final não root. Auth tem bases por digest e
entrypoint `java -cp /app/app.jar br.com.fiap.oficina.auth.infrastructure.internal.InternalAuthMain`,
preservado. OS/Execution/Billing ainda usam bases por tags: registrar os IDs
locais e revisar pin por digest nos repositórios proprietários para repetibilidade
mais forte. Nenhum Dockerfile de aplicação foi editado.

O publicador local exige bases já presentes, usa `--network=none --pull=false`,
labels OCI source/revision, inspeciona usuário/plataforma/labels e exporta image.tar.
Verifica hash do config contra image ID, diff_ids dos layers e scanner de conteúdo,
incluindo JARs aninhados. Não publica tag latest e não usa imagem antiga do target.
Dockerfiles que usam COPY target local ou COPY de contexto inteiro são recusados.
Dependências ausentes bloqueiam o build offline; não são baixadas silenciosamente.

Os POMs observados dos quatro serviços declaram JaCoCo 80% no verify. Auth possui
workflow CI/CD legado que faz clean verify e também deploy em push: não foi
alterado/habilitado e não deve ser reutilizado na Fase4 sem autorização específica.
Os SHAs inspecionados dos três microsserviços não contêm `.github/workflows`.
CI por serviço ainda precisa ser preparada nos repositórios proprietários;
esta etapa não cria workflows, nem executa publicação em push.

## 4. Auth público e layer

Auth gera efetivamente `target/tech-challenge-oficina-auth.jar`; arquivos
`original-*` são excluídos da seleção. Para os outros serviços o script exige
exatamente um JAR final efetivamente gerado, sem presumir nome baseado no projeto.
O validador confirma formato ZIP/JAR, tamanho, bytecode Java21 do handler,
`br.com.fiap.oficina.auth.handler.AuthHandler::handleRequest`, classe interna,
dependências shaded e ausência de harness/JUnit/Testcontainers no pacote produtivo.
Não modifica handler, entrypoint interno ou contratos públicos.

A layer contém exatamente:

```text
bin/auth-bootstrap                      0755, LF
java/lib/auth-bootstrap.jar             0644
auth-home/.postgresql/root.crt           0644
```

`AWS_LAMBDA_EXEC_WRAPPER=/opt/bin/auth-bootstrap` e
`JAVA_TOOL_OPTIONS=-Duser.home=/opt/auth-home` são os valores atuais da Edge.
O wrapper faz exec do runtime original preservando seus argumentos; captura a
senha do helper em memória, valida formato e não a imprime em stdout/stderr.
O helper valida scope/Secret ID/usuário, JSON estrito e CA legível, usando o
cliente HTTP URLConnection explicitamente selecionado.

O teste de empacotamento revelou que o SDK transitivamente incluía Netty,
inclusive material privado público de teste em OpenSsl.class. O POM **da Infra**
agora exclui `netty-nio-client` e `apache-client`, não utilizados pelo helper
síncrono. URLConnection foi mantido; nenhum POM de aplicação foi editado.
O mesmo achado no JAR Auth requer revisão do proprietário Auth antes de aprová-lo.

O script compila o helper a partir do snapshot do SHA Infra, não recebe um JAR
arbitrário como prova de origem. Produção exige checkout limpo. Modo `--fixture`
pode empacotar ajustes locais da pasta bootstrap, mas registra os hashes de cada
arquivo em `uncommitted_fixture_sources`, com estado `fixture_only`: não declara
que as mudanças locais pertencem ao commit-base nem permite aprovação/publicação.

## 5. CA RDS

`rds-ca-policy.json` inicia vazio: **nenhuma CA RDS está aprovada**. Não houve
download de CA ou consulta AWS. Apenas um marcador explícito
`FIXTURE_NOT_AN_RDS_CERTIFICATE` foi usado para testar layout/permissões/LF.
Ele não é certificado e nunca pode ser tratado como CA RDS válida.

Para pacote operacional, o bootstrap precisa obter o bundle público regional de
fonte aprovada, validar X.509/validade/CA/chain, revisar checksum e registrar no
allowlist a origem exata
`https://truststore.pki.rds.amazonaws.com/us-east-1/us-east-1-bundle.pem`, região
e SHA-256. O validador confere esses bytes contra o allowlist e rejeita material
privado. Um parâmetro de usuário não pode aprovar CA desconhecida.
A validade operacional da cadeia precisa ser reavaliada antes do deploy.

## 6. Manifesto JSON v1 e proveniência

Campos principais: schema_version, created_at UTC, scope, infra, applications,
artifacts. Cada artefato identifica tipo, repository, SHA completo, Java21,
linux/amd64, estado, evidência local e referência remota separada.

| Estado conceitual | Evidência exigida | Disponível nesta etapa |
| --- | --- | --- |
| planned | Identidades completas, nenhum checksum inventado | Sim, inclusive planejamento offline para ambiente disabled |
| built_tested | Bytes reais, checksum/tamanho, recibo íntegro, snapshot, testes/cobertura e validação do pacote | Aplicações quando todos os gates passam |
| published | Escrita autorizada e releitura efetiva do destino remoto | Não; rejeitado pelo validador offline |
| deploy_approved | Publicado verificado, CA/runtime/JWT/Infra/Platform/Edge e dependências prontas | Não; rejeitado nesta entrega |

`local` e `remote` são null no planejamento. Evidência local inclui file, size,
sha256, receipt e receipt_sha256. A validação relê bytes/recibos/relatórios e
snapshot, compara SHA do git archive e comentário de revisão, e rejeita alterações
nas fontes de build após extração. Snapshot e recibos devem permanecer sob
custódia do mesmo job aprovado. Isso não é assinatura de supply chain nem protege
contra um operador malicioso que forje todo o diretório de evidências.

`verify` retorna o SHA-256 canônico do manifesto. Guardar esse valor na evidência
do job e fornecer `--expected-sha256` no consumo posterior detecta alterações.
Simulação captura o fingerprint e o compara novamente antes de devolver resultado.
JSON duplicado, campos extras, credenciais, paths fora do diretório de release,
origem/arquitetura divergentes e hashes incorretos são recusados.

Planejar para demo-a não aprova sua conta: o catálogo ainda tem conta null.
A fixture de request usa `123456789012` como conta **sintética**, somente para
planejamento/testes. Operação futura exige enabled=true e conta exata aprovada.
Nenhum manifesto local promove fixture, layer apenas empacotada ou campo
`verified=true` para publicado/aprovado.

## 7. Identificadores distintos

| Identificador | Significado |
| --- | --- |
| SHA Git de 40 caracteres | Revisão de um repositório específico |
| SHA-256 do arquivo | Bytes reais do JAR, ZIP, snapshot ou image.tar |
| Docker image ID | SHA-256 do config local; não é digest de registry |
| Digest OCI/ECR | Manifesto consultado no registry após publicação |
| S3 VersionId | Identidade real retornada pelo S3 versionado; não é checksum |
| LayerVersionArn | Versão imutável retornada pela Lambda; não é revisão Git |

Não inferir digest remoto a partir de tar/config local. Uma publicação com OCI
index/attestations pode ter digest distinto do manifesto por plataforma. A
simulação atual aceita somente manifesto single-platform com config digest
coerente e rejeita index não resolvido; futuro adaptador deve resolver o filho
linux/amd64, validar sua relação com o index e registrar ambos.

## 8. Contrato ECR futuro

O futuro job manual/condicionado resolve catálogo aprovado e observa STS/OIDC
na role `<prefix>-deploy`, conta/região reais. Confirma os quatro repositórios
exatos, mutability IMMUTABLE e ownership. Confere snapshot, image ID, labels e
linux/amd64; autentica via GetAuthorizationToken e password-stdin, em
DOCKER_CONFIG temporário, sem imprimir/guardar token ou usar access keys permanentes.

Tag será o SHA completo da aplicação. Tag já existente com conteúdo diferente
é conflito, nunca autorização para sobrescrever ou alterar mutability.
Publicação futura consulta DescribeImages por tag, BatchGetImage por digest,
rehash do manifesto retornado, associação ao config local e nova consulta por
tag/digest após conclusão. Exporta Platform somente `<ECR exato>@sha256:<real>`.
Não preencher digest para desbloquear Deployment sem publicação real.

`OfflinePublisher.simulate()` usa clientes injetados nos testes. Confere
identidade observada sintética, destinos, tags, digest do manifesto e config;
seu resultado tem sempre mode=simulation, publish_allowed=false e
deploy_allowed=false. Observações mockadas não alteram o manifesto para published.
Não existe transporte AWS operacional nesta entrega.

## 9. S3/JAR e Lambda layer futuros

Bucket exato `<prefix>-artifacts`, regional, privado, versionado. Chave JAR:
`auth/<SHA Auth>/auth.jar`. Put futuro precisa ser condicional, impedir
substituição de conteúdo na chave imutável e tratar reexecução somente após
reler/verificar a versão anterior. Exigir ExpectedBucketOwner, região,
Public Access Block e versionamento; não criar bucket durante publicação.

Após Put, reconsultar bytes/checksum e VersionId real, depois GetObject da versão
exata e revalidar. Não inventar VersionId nem usar ETag como SHA-256.
Após PublishLayerVersion real, consultar GetLayerVersion, CodeSha256, runtime,
arquitetura, proveniência e bytes pelo destino retornado; validar CA/wrapper.
Reexecução da layer usa evidência existente por checksum/revisão, não cria versões
ilimitadas sem consultar equivalência. Registros de publicação devem ser imutáveis.

A simulação testa ownership via ExpectedBucketOwner, bloqueio público,
versionamento, duas leituras S3 da versão e ARN/runtime/arquitetura da layer.
Ela **não** certifica a layer: mantém bloqueadores explícitos de CA, runtime,
checksum/bytes remotos e prova real de publicação. `auth-layer` permanece planned
no manifesto offline; seu recibo fixture fica separado e não gera auth_release.

## 11. Integração Infra/Platform/Edge e bloqueadores

Infra mantém ECR IMMUTABLE; sua lifecycle policy retém dez imagens por ambiente:
releases antigas podem perder imagem. Antes de promover/rollback, consultar
existência novamente e revisar retenção de digests ainda em uso.
Platform exige quatro digests ECR exatos, mais imagens verificadas de dados,
auth_image_verified e guards de migração/bootstrap/Secrets/PKI/network policy.
Não produzir flags readiness=true apenas a partir do manifesto.
Edge exige auth_release com bucket/key/VersionId/SHA base64, revisão Auth e
LayerVersionArn/revisão Infra reais, além de seus guards operacionais.

Issuer deve ser o endpoint HTTPS real do API Gateway e audience `<prefix>`;
JWKS deve ser `<issuer>/.well-known/jwks.json`. Simulação rejeita divergências
Platform/Edge. Não usar URL fixture ou ARN/digest inventado em Terraform operacional.

| Bloqueador | Responsável pela resolução |
| --- | --- |
| Catálogo disabled, conta/backend não aprovados | Operação/owner Infra, etapa autorizada |
| Imagens novas não construídas/publicadas/verificadas | CI dos quatro proprietários + publicador manual futuro |
| Auth contém dependência Netty com material de teste detectado | Owner Auth, revisar/excluir clientes transitivos não utilizados no POM proprietário |
| OS/Execution também empacotam material de teste Netty detectado | Owners OS/Execution, analisar grafo de dependências e tratamento seguro sem remover dependência necessária cegamente |
| Billing sem dependência disponível no cache offline | Owner Billing/CI, preparar cache aprovado antes de repetir clean verify |
| IT Auth interno condicionado à imagem produtiva | Owner Auth/CI, executar com imagem nova e evidência de aprovação |
| CI ausente nos três SHAs de microsserviços | Owners OS/Execution/Billing, revisão própria sem deploy em push |
| Bases Docker necessárias não disponíveis offline/pins por tag | Owners das aplicações, aprovar pins/cache de dependências |
| CA RDS definitiva e allowlist vazia | Bootstrap/segurança Infra, obter e revisar bundle público regional |
| Bucket de artefatos sem owner Terraform | Bootstrap persistente Infra, revisão mínima descrita acima |
| IAM/OIDC efetivo e leituras de bucket não comprovados | Owner identities, revisão/teste AWS autorizado posterior |
| auth-signing e auth-postgres sem evidência nesta etapa | Operação Secrets/PKI 9.2.3.3, sem inserir payload em artefatos |

## 12. Uso local e CI futuro

Requer Python 3.13, Git, JDK21, Maven e Docker Linux para builds de imagem.
Sem dependência Python adicional. Exemplos a partir da root Infra:

```text
python scripts/artifact-release/release.py plan --request scripts/artifact-release/fixtures/request.json --output <temporario>/planned.json
python scripts/artifact-release/release.py build-app --service auth --repository <checkout-auth> --revision <SHA completo> --output <temporario>/auth
python scripts/artifact-release/release.py layer --revision <SHA Infra limpo> --ca <bundle aprovado> --output <temporario>/layer
python scripts/artifact-release/release.py attach --manifest <planned.json> --service auth --receipt <temporario>/auth --root <temporario> --output <next.json>
python scripts/artifact-release/release.py verify --manifest <next.json> --root <temporario> --expected-sha256 <hash previamente registrado>
python scripts/artifact-release/release.py publish
```

O último comando sempre falha. `--git`, `--java`, `--maven` e `--docker` permitem
caminhos explícitos de ferramentas instaladas. Layer também aceita caminhos Git/
Java/Maven. `--fixture` permite somente o marcador CA conhecido e recibo fixture.
Outputs devem ser novos; scripts recusam sobrescrever diretórios/manifestos.
Depois de corrigir bloqueadores, usar uma nova execução, sem alterar recibos anteriores.

Futuro CI pode testar/analisar automaticamente por serviço; coleta recibos de
snapshots exatos em jobs separados. Publicação deve ser manual/condicionada por
GitHub Environment protegido e OIDC; deploy manual separado consome apenas prova
remota realmente verificada. Não reativar workflow legado em push normal.
