## 4. Provisionamento e boundaries

`policies.tf`/`operations.tf` declaram ações de criação/configuração e leitura de
Infra/Platform/Edge. Nomes de EKS/RDS/ECR/Lambda/roles são derivados do ambiente.
Criação EC2 exige tags EnvironmentId/Phase/Lifecycle; configuração usa ownership
do recurso. SG gerenciado pelo EKS usa a tag reservada aws:eks:cluster-name exata.
Mudança/remoção de tags de ownership EC2 fora da criação é negada.

IDs opacos de rede, API/VPC Link, filhos EKS, RDS e Secrets usados para permissões
adicionais/delete entram por inventário público **observado e revisado**. Não
basta preencher um ARN sintaticamente válido: conferir conta/região/VPC, relação
com cluster/RDS, nome, tags/UIDs e propriedade por fonte independente. Script
Secrets9.2.3.3 continua verificando MasterUserSecret do RDS e ownership canônico.
Campos estrangeiros/tipos não autorizados/ARNs com wildcard são recusados.

API Gateway CreateApi restringe apigateway:Request/ApiName ao nome Edge exato;
CreateVpcLink usa tags de criação. Atualização/sub-recursos exigem ARNs completos
inventariados, incluindo collections e stage `$default`. APIs/VPC Link têm IDs
gerados: observar/autorizar esses IDs é checkpoint antes de configurar rotas.
Não existe regra DELETE genérica por prefixo ou API descoberta por tags apenas.
As condições suportadas são conferidas na
[referência API Gateway V2](https://docs.aws.amazon.com/service-authorization/latest/reference/list_apigatewayv2.html).

Provision não pode criar roles arbitrárias nem passar a própria role. CreateRole
só é emitido para workload com boundary aprovada/documento correspondente:

- eks-cluster, eks-nodes: Infra;
- ebs-csi, load-balancer-controller: Platform;
- auth-lambda: Edge.

`workload_boundary_documents` contém somente IAM JSON público revisado, criado
sob nome persistente `<prefix>-<workload>-boundary`; sem Action wildcard,
NotAction, sts:AssumeRole ou administração IAM (exceto CreateServiceLinkedRole,
que ainda exige revisão estrita de recurso/condição). Não contém credenciais.
Passar seus ARNs pelos inputs de boundaries das stacks; variáveis default vazias
preservam chamadas locais antigas, mas **a role automatizada não cria role sem
boundary**. Não se deve usar um operador admin para contornar essa negação.

Preparar boundaries progressivamente: cluster/nodes primeiro; CSI/Auth conforme
contratos conhecidos; ALB depois do SG/certificado observados. Não exigir cinco
workloads existentes para criar a primeira role. Os documentos produtivos não
foram inventados: precisam incorporar ações reais dos managed policies atuais
e policies locais, com recursos/condições revisados e teste IAM autorizado.
Fixtures read-only dos testes não são boundaries funcionais de runtime.

PutRolePolicy/UpdateAssumeRolePolicy limitam-se às cinco roles efêmeras, sob o
limite das boundaries. AttachRolePolicy limita-se aos quatro managed policies
selecionados, não AdministratorAccess. Put/DeleteRolePermissionsBoundary negados
ao provision. Operador persistente continua privilegiado: proteger seus reviews,
session logs, documentos e backend; estes controles não tornam IaC não confiável seguro.

Policies da automação são particionadas em managed policies (até8 statements por
parte), com precondition de6144 caracteres e até10 attachments por role. Validar
novamente com inventário real; guard bloqueia estouro, não aumenta quotas.

## 6. EKS Access Entries e fase privilegiada

Infra continua authentication_mode=API e bootstrap_cluster_creator_admin_permissions=false.
`automation_roles` recebe os três ARNs persistentes exatos. Access Entries
deploy/destroy usam grupo `oficina:<env>:executor`, sem access policy gerenciada
aditiva. `eks_admin_role_arn` deve ser a role provision quando automação estiver
configurada. Entrada provision usa grupo bootstrap sem binding privilegiado permanente.

Associação AmazonEKSClusterAdminPolicy agora tem
`cluster_bootstrap_access_enabled=false` por padrão. Elevação exige job provision
aprovado e janela explícita para Namespace/StorageClass, CRDs, ClusterRoles,
webhooks, controllers e aplicação inicial de RBAC. Ao terminar, remover associação
e comprovar ListAssociatedAccessPolicies e negativas efetivas. Não basta terminar
o job ou confiar na expiração do JWT: a associação não possui TTL nativo.

Se bootstrap for interrompido, bloquear novos jobs e exigir revogação comprovada
pelo operador persistente; incluir essa pendência no lease/runbook. Recuperação
de endpoint não implica revogação RBAC. A permissão de elevar a própria role
provision é privilegiada deliberadamente e exige proteção independente do Environment.

Token Kubernetes será `aws eks get-token` com sessão OIDC temporária; não criar
token ServiceAccount permanente nem alterar aws-auth legado. IAM autentica,
RBAC autoriza; access policies EKS são aditivas e não devem permanecer para
"compensar" um Role faltante. Ver
[Access Entries](https://docs.aws.amazon.com/eks/latest/userguide/creating-access-entries.html).

## 7. RBAC de deploy/destroy

`executor_rbac` é output List JSON separado:6 objetos,2 Roles/RoleBindings e
ClusterRole/Binding de evidências. Não altera os bundles já aprovados da Platform.
Aplicar inicialmente somente na fase privilegiada.

- Namespace de negócio `<prefix>` e observabilidade `<prefix>-observability`.
- CRUD de ConfigMaps, Services, ServiceAccounts, PVCs, Deployments, StatefulSets,
  ReplicaSets, Jobs, Ingresses e NetworkPolicies; leitura de pods/events/endpoints/logs.
- Secrets: create no namespace; get/update/patch/delete somente nomes esperados.
  Sem list/watch de Secrets. Observabilidade usa `newrelic-license`.
- RBAC não restringe create por nome/label: executor continua autoridade sensível
  no namespace. Scripts9.2.3.3 validam ownership/UID antes de substituir/excluir;
  namespace com Pod Security restricted e apps sem IAM/token limitam escalada.
- Evidência cluster-scoped somente leitura de nodes/PVs/namespaces e get das
  StorageClass/IngressClass próprias. Sem escrita cluster-scoped, pods/exec,
  impersonate, bind, escalate, roles ou rolebindings.

E2E e pós-condições devem usar Jobs observáveis. Instalar charts que criam RBAC,
CRDs, DaemonSets privilegiados/kube-system ou realizar teardown de namespaces/
classes/controllers exige fase provision privilegiada separada; a role namespaced
não é suficiente. Destroy retira apps/PVCs sob RBAC e mantém CSI/ALB controller até
cleanup físico; fase privilegiada posterior remove recursos cluster-scoped.

## 8. ALB Controller e outros addons

Platform é o único dono de `aws_iam_role.alb_controller`, inline policy e
`aws_eks_pod_identity_association.alb_controller`. Edge apenas referencia o contrato.
`alb_controller_identity_enabled=false` por padrão; habilitação exige SG Edge
observado na VPC/namespace/EnvironmentId corretos e ACM da conta/região.
Role: `<prefix>-load-balancer-controller`, SA kube-system/aws-load-balancer-controller.
Trust exige pods.eks.amazonaws.com, AssumeRole/TagSession e request tags exatas
de ARN cluster/namespace/SA; manter session tags habilitadas.

Policy preparada em `modules/alb-controller-policy`, baseada em upstream
v2.14.0/chart1.14.0, sem baixar "latest". CreateLoadBalancer exige internal,
subnets privadas e SG Edge (ForAllValues + Null para não aceitar lista ausente),
nome ALB exato, tags de cluster/ambiente. Listener inicial HTTPS. Modificações/
delete do ALB e target groups exigem ownership; listeners/regras têm ARN app do
ALB exato, não permissão universal. Ownership tags não podem ser retagged depois.

Sem WAF/Shield/Cognito, SLR IAM automático pelo pod, certificado IAM ou escrita
EC2 SG. Platform aplica overlay enableShield/enableWaf/enableWafv2/
enableBackendSecurityGroup=false; Edge já gerencia SGs. SLR ELB deve existir por
bootstrap/provision autorizado antes do controller.

EC2/ELB Describe permanecem Resource* regional. AWS ELBv2 não oferece condição
Vpc para CreateTargetGroup: não fingir esse enforcement; VPC vem do cluster/
controller configurado, SG/subnets vinculam ALB, e RBAC/admissão precisam impedir
IngressGroup estrangeiro. Tags não substituem trust nem inventário operacional.
Referência [ELBv2](https://docs.aws.amazon.com/service-authorization/latest/reference/list_elbv2.html).
IAM simulado localmente não prova reconciliação real, SAN ou reachability de pods.

EBS CSI já possui role/associação própria e policy ClusterScoped, agora aceita
boundary. Pod Identity Agent não ganha role admin: usa suporte eks-auth da policy
dos nós. VPC CNI permanece com AmazonEKS_CNI_Policy nos nós nesta etapa; segregar
CNI futuramente exige revisão própria, não reuso da role ALB. Apps não recebem
IAM de controller. New Relic atual não exige IAM AWS; RBAC de chart requer revisão.

## 9. Secrets, PKI e KMS

Nomes canônicos são allowlist explícita, incluindo technical-ca e finalidades
runtime/migration/certificados; auth-signing e master RDS não pertencem ao conjunto
destrutivo normal. ARNs de criação têm somente seis caracteres de sufixo SM
variáveis, não prefixo amplo de todos os Secrets. Leitura/deleção usam ARNs completos
observados, com EnvironmentId correto. Master read é exceção explícita por ARN,
conferida com DescribeDBInstances pelo transporte aprovado; remover grant após bootstrap.

CreateSecret/TagResource são separados de GetSecretValue; PutSecretValue exige
rotate_secret_names e inventário aprovado. Não autorizar UpdateSecret, resource
policies, replicação ou DeleteSecret no deploy por conveniência. Delete só no
destroy confirmado, sem wildcard, sem credencial master e sem assinatura.
Revisar os tags completos ManagedBy/Owner/Purpose/Consumers/ProjectionLifecycle
dos scripts, não apenas o tag IAM EnvironmentId.

Assinatura RS256 continua propriedade do emissor: role Lambda Auth lê auth-signing;
executor Platform não lê/cria/rota/apaga essa fonte. Instalação/encerramento dessa
fonte exigem identidade emissora aprovada separadamente (não reutilizar role Auth
legada ampla). Essa integração permanece dependência do pipeline Auth.

Default aws/secretsmanager gerenciado pelo serviço não recebe grant Decrypt
universal. RDS requer DescribeKey para a chave gerenciada, além de CreateSecret/
TagResource; ver [RDS e Secrets Manager](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-secrets-manager.html).
CMK própria exigirá ARNs/key policy e Decrypt/GenerateDataKey por consumidor,
ViaService e encryption context apropriados, após avaliação; não antecipados aqui.

Nenhum data source SecretVersion, SecretString, password ou chave privada entra
no Terraform. IAM JSON/ARNs são configuração pública. Fontes/projeções/mTLS e PKI
mantêm9.2.3.3: CA48h padrão/máximo72h, validade suficiente para toda a operação,
renovação coordenada, nunca regeneração silenciosa. Kubernetes Secrets dependem
de RBAC/criptografia em repouso, não de base64.

## 11. Acesso temporário EKS

Privado continua default na Infra; público somente IP observado /32 e privado
ativo. **Nenhuma role GitHub recebeu permissão ativa de abrir endpoint.** Provision
só pode UpdateClusterConfig com public=false/private=true explícitos; pedidos
omitindo esses bools são negados, inclusive atualizações Terraform de logging
que não tragam esse contexto. Não suavizar para BoolIfExists: um pedido apenas de
CIDR poderia ampliar acesso durante lease ativo. Mudanças não-endpoint precisam
de caminho privilegiado/revisão próprios antes de serem automatizadas.

AWS agora documenta bool keys endpointPublicAccess/endpointPrivateAccess, mas não
condition key para validar publicAccessCidrs. Logo não é honesto dizer que uma
role com UpdateClusterConfig bruto impede0.0.0.0/0 por IAM. O output
endpoint_broker_candidate é apenas policy **não anexada**, não autorização ativa.

`scripts/identity-contracts/contracts.mjs` valida catálogo/conta/região/cluster,
IPv4 público observado igual ao /32 e lease de1–30min, mas retorna sempre
dispatch_allowed=false porque recuperação durável não foi implementada.
O IP deve ser observado no próprio runner por canal HTTPS aprovado, não escolhido
por input; reobservar ao mudar job/runner. IP sintético dos testes não é observado.

## 12. Recuperação independente: bloqueador obrigatório

Role persistente `<prefix>-endpoint-recovery` confia apenas em Lambda AWS, não
em GitHub, sem Access Entry. Tem três leituras EKS e UpdateClusterConfig apenas
do cluster exato, com public=false/private=true. Não pode abrir outro cluster,
ler Secrets, destruir Infra nem assumir role operacional.

Permissões futuras de lease/logs/retry exigirão ARNs próprios e revisão no
bootstrap persistente: não há grants DynamoDB/Scheduler/logs universais nesta role.

**Não existe Lambda/Scheduler/lease instalado.** Preparou-se a identidade e desenho,
não o mecanismo operacional. Nenhum workflow futuro pode abrir endpoint enquanto
esse bloqueador existir, nem aceitar booleano arbitrário como evidência de recuperação.

Desenho mínimo para próxima autorização:

1. Broker Lambda fora da VPC, com payload fixo, verifica identidade/ambiente,
   IP observado /32 e configuração privada anterior. Nenhuma role GitHub recebe
   UpdateClusterConfig aberto; invoca broker autenticado e restrito ao ambiente.
2. Lease durável com prazo explícito, lock condicional por cluster/lease_id e
   metadados públicos (conta/ARN/IP/revisão/run/expiração/configuração anterior).
   DynamoDB simples pode guardar lease/estado; TTL não será usado como timer.
3. Criar e confirmar one-time EventBridge Scheduler **antes da abertura**,
   invocando Lambda recovery do ambiente. Invoker separado só InvokeFunction
   nessa função, trust Scheduler restrito a conta/grupo. Não depender de outro job GitHub.
4. Recovery confere ARN/lease atual, pede public=false/private=true com parâmetros
   fixos, aguarda DescribeUpdate, reobserva DescribeCluster e registra evidência.
   Restaurar/remover /32 conforme configuração fechada aprovada e sem ampliar CIDR;
   validar comportamento da API com lista vazia antes de escolher esse payload.
5. Retry/DLQ/alarme e responsável definidos; lease não fecha só por expiração.
   Não iniciar nova abertura enquanto fechamento anterior não estiver comprovado.
   Isso evita que timer antigo feche operação nova ou que cancelamento perca recuperação.
6. Cleanup normal/finally continua útil, porém confirmação independente sobreviverá
   ao runner. Em falha bloquear novos jobs, manter identidades/lease e acionar operador.

Scheduler/Lambda/store têm custo por uso/armazenamento; justificar janela curta,
uma recuperação por lease e retenção mínima antes de criar. Nada disso foi
adicionado às stacks efêmeras ou presumido operacional. IAM não restringe todos
os demais campos UpdateClusterConfig: handler fixo é controle necessário adicional.

## 13. Ordem operacional e destroy

Criação: bootstrap persistente/OIDC/proteções → boundaries revisadas de cada fase
→ Infra/Access Entries → recuperação durável comprovada → lease /32 → bootstrap
Kubernetes privilegiado/CRDs/controllers/RBAC → revogar elevação → Secrets/PKI/
bancos/migração → workloads/Edge e E2E namespaced → fechar endpoint e verificar
independentemente. Não existe workflow operacional nesta revisão.

Destroy: aprovação GitHub Environment distinto, ambiente/conta exatos,
`DESTROY <env> <account> <prefix>` e inventário independente revisado. Desativar
rotas Edge antes de remover integrações/VPC Link. Manter controller ALB até
finalizers e confirmação real de ALB/listeners/target groups/ENIs. Remover apps,
PVCs e confirmar EBS excluídos com CSI ainda ativo. Fase privilegiada aprovada
remove controllers/CRDs/RBAC/namespace/classes depois; role destroy remove AWS
do inventário e Infra por último. Guard não confunde state com remoção física.

Role destroy não recebe DeleteVolume/DeleteNetworkInterface genéricos: serviços/
CSI fazem cleanup normal, e órfão exige recuperação específica revisada por ARN.
Secrets do inventário só saem após últimos consumidores. Master RDS acompanha RDS;
auth-signing/artifact versions exigem pipeline emissor/cleanup autorizado próprios.
Logs persistentes de recovery/lease e identidades de automação sobrevivem até
fechamento final comprovado; Environment Destroy não destrói bootstrap.
